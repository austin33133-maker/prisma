## 1. 域划分

Schema 按五个域组织,对应开发方案中的子系统:

```
用户与商业化域      User · Plan · Subscription · UsageRecord
商品目录域          Marketplace · Category · Product · ProductDailyMetric
关键词域            Keyword · KeywordDailyMetric · KeywordRanking
追踪与告警域        ProductTracker · KeywordTracker · Alert
采集域              CrawlTask
```

## 2. 关键设计决策

### 2.1 ASIN 不是全局主键

同一 ASIN 在不同站点是不同的商品(价格、类目、评论独立),所以 `Product` 用代理主键 + `@@unique([marketplaceId, asin])`,所有指标和排名都挂在 `Product.id` 上。`Keyword` 同理按 `@@unique([marketplaceId, text])` 区分站点。

### 2.2 时间序列表用复合主键,不用代理键

`ProductDailyMetric`、`KeywordDailyMetric`、`KeywordRanking` 以 `(实体 ID, date)` 作为 `@@id`:

- 天然幂等——重复采集同一天的数据是 upsert 而不是重复行;
- 与未来迁移目标 ClickHouse 的 `ORDER BY` 键一一对应,迁移时 Prisma 模型直接退化为类型契约(见开发方案 §2.2)。

`KeywordRanking` 的主键额外包含 `isSponsored`,因为同一商品同一天可以同时占据自然位和广告位。

### 2.3 反查 ASIN 是索引设计而不是新表

反查 = 对 `KeywordRanking` 按商品倒排,因此建 `@@index([productId, date])`;正向的关键词排名追踪走主键前缀。一张表服务两个核心功能。

### 2.4 套餐只建模额度,不建模功能开关

`Plan` 上是 `maxTrackedProducts`、`dailyReverseLookups` 等数值列,没有 feature flag——对应调研结论「付费版功能全量开放,套餐差异在额度」。额度校验逻辑 = `Plan` 的上限 vs `UsageRecord` 的 `@@unique([userId, action, day])` 聚合计数,新增计费动作只需要新的 `action` 字符串,不动 schema。

### 2.5 告警阈值与触发现场用 Json 列

`ProductTracker.alertConfig` 与 `Alert.payload` 是用户/事件维度的半结构化数据,形状随告警类型(`AlertKind`)不同而不同,演进频繁,不值得为每种告警建列。结构校验放在应用层(zod)。

### 2.6 销量预估可回溯

`ProductDailyMetric.estimateModelVersion` 记录每行估算值出自哪个模型版本。预估算法是口碑生命线(调研 §5),必须能区分「数据变了」和「模型变了」,才能做回溯校准与 A/B。

### 2.7 子账号用自引用

`User.parentId` 自引用支撑代运营/团队场景,子账号数量上限由 `Plan.maxSubAccounts` 控制,不需要独立的 Organization 模型——卖家精灵的团队形态就是「主账号 + 子账号」,先不过度设计。

## 3. 容量预估与演进路径

| 表 | 量级(MVP,美国站) | 演进 |
|---|---|---|
| Product | ~2000 万行 | 留在 PostgreSQL |
| ProductDailyMetric | 2000 万 × 采集频率,月增数亿行 | **第一个迁 ClickHouse 的表** |
| KeywordRanking | 关键词池 10 万 × 每词 Top 100+,日增千万行 | 同上 |
| 用户域全部 | < 百万行 | 永久留在 PostgreSQL |

迁移触发条件:单表超过 ~5 亿行或图表查询 P95 > 1s。迁移后 PostgreSQL 中对应模型删除,Prisma 类型由 ClickHouse 查询服务的 DTO 接管。
